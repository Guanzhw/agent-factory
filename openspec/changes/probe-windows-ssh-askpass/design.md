## Carrier and explicit tradeoff
Generate a synthetic key and a fresh 32-byte random passphrase per invocation. Encode the passphrase as fixed-length ASCII for OpenSSH ASKPASS. Serialize only encrypted OpenSSH private-key bytes into a creation-time current-token-user-only protected-DACL directory/file. Validate owner/DACL and reject reparse paths before writing. No plaintext private key or passphrase file. The already rejected DELETE_ON_CLOSE carrier is not retried.

Normal exit deletes this invocation's files. Hard process termination may leave encrypted bytes; this is an accepted probe tradeoff, not a zero-residue claim. There is no stored recovery passphrase. The probe does not promise protection against privileged/current-user memory inspection, swap or crash dumps. A later product path would reuse the existing vault and authorization checks, without creating a grant or changing credentials.

## Fixed helper, not a new agent
A tiny test-only Python package provides one installed Windows console-entry executable. Use existing packaging tools/dependencies, not a custom native launcher or shell script. Its absolute trusted installed path is the only SSH_ASKPASS value. No arbitrary helper selection, shell expansion or prompt-driven command.

The first actual Windows observation must establish the exact entry-point process shape. Only two explicit shapes are candidates: direct helper process, or installed launcher -> Python helper process. No arbitrary-depth ancestor traversal. Check the actual pipe client token user SID once. For each process in the fixed chain, open and retain its OS handle, check QueryFullProcessImageName, process creation time and parent relationship; the root must be the exact still-live system ssh-keygen/ssh.exe process handle created by this invocation. Reject any other shape. Compare process times to prevent accepting a reused parent PID. Public expected image paths and pipe identifiers are not credentials.

## One-use local pipe
The controller creates one random-name pipe with protected current-user DACL, FILE_FLAG_FIRST_PIPE_INSTANCE and PIPE_REJECT_REMOTE_CLIENTS. The pipe name and controller PID may be passed in the child's environment; neither is a bearer credential. No passphrase in argv, environment, file, diagnostic, or model input.

The broker obtains the connecting client's PID using GetNamedPipeClientProcessId, and checks the exact fixed helper chain above. The helper obtains GetNamedPipeServerProcessId and checks the expected controller PID and that its process handle remains live. It does not duplicate the server-side image/SID/creation checks. Do not trust an identity asserted in pipe payload. One authorized release of a fixed-length passphrase, then close; rejected callers receive no bytes. A second request, invalid/confirmation prompt or timeout fails closed. Use bounded overlapped pipe operations so a wrong/stalled client cannot block controller shutdown. The helper writes only passphrase plus newline to OpenSSH's own private stdout pipe; never to CI stdout.

## Process lifetime
The broker is a thread of the controller, never an independently surviving service. The controller owns a Windows job with KILL_ON_JOB_CLOSE and non-inheritable handles. Create the system OpenSSH process suspended, assign it to that job before execution, then resume; descendants inherit the job. No breakaway. On normal timeout/error, terminate and reap the owned job/processes; on controller hard termination the job handle closes and kills SSH/helper descendants. Test actual assignment on the runner; inability to use this job arrangement is an incomplete experiment, not permission to leave orphan passphrase holders. Keep the IPC and key-loader deadlines below the outer 60-second stage budget.

## Stage A: exact system loader and IPC
- Use installed System32/OpenSSH binaries, record OS/OpenSSH versions. Missing prerequisites are BLOCKED.
- Run actual ssh-keygen -y on the encrypted key with SSH_ASKPASS_REQUIRE=force and the fixed helper; no -P passphrase and no console/stdin fallback. The comparison to the in-memory public key is boolean only.
- Demonstrate wrong client identity receives zero bytes, one legitimate release succeeds, repeated request gets zero bytes, and a stalled helper ends within the deadline.
- Kill the controller at a controlled point after the real helper has received the passphrase but before it forwards it to OpenSSH or exits. Confirm job descendants stop, no plaintext file exists, and any remaining key bytes are the encrypted serialization. Do not claim the original key has become cryptographically unrecoverable to a party who captured process memory.

## Stage B: actual public-key SSH, only after A
Use existing system sshd.exe in foreground with a private temporary configuration, synthetic host/authorized keys, loopback high port and the existing test account. Do not install/start a system service, modify global authorized_keys, create users or adjust privileges. If this cannot start under existing runner permissions, mark B BLOCKED and report the exact prerequisite; do not build a replacement SSH protocol server.

System ssh.exe arguments retain strict host pin and -F none, IdentitiesOnly=yes, IdentityAgent=none, no agent forwarding/proxy/control multiplexing/local command. Use BatchMode=no to allow encrypted-key prompting, PreferredAuthentications=publickey, PasswordAuthentication=no, KbdInteractiveAuthentication=no, NumberOfPasswordPrompts=1 and SSH_ASKPASS_REQUIRE=force. Only a fixed passphrase prompt is eligible; confirmation/notification prompts get no response. There must be no visible console prompt or alternate authentication. Test correct authentication, wrong host pin with zero broker release/command execution, and refusal of an extra ASKPASS request. No Linux helper or GPU acceptance is claimed by this Windows loopback test.

## Sources and remaining evidence
Official Windows OpenSSH readpass.c has a Windows posix_spawn ASKPASS branch and force selection: https://github.com/PowerShell/openssh-portable/blob/latestw_all/readpass.c . sshconnect2.c stops encrypted-key prompts under BatchMode: https://github.com/PowerShell/openssh-portable/blob/latestw_all/sshconnect2.c . These sources establish a candidate mechanism, not installed-version success. The system agent's registry persistence remains excluded. The actual launcher shape, process job behavior, named-pipe identity checks and force/publickey-only behavior must all be measured before product integration.

## Required encryption dependency (first-run correction)
The first Stage A run failed before OpenSSH at encrypted serialization because cryptography's optional OpenSSH bcrypt KDF dependency was not installed. Add only a dedicated `ssh-probe` dependency group with `bcrypt==5.0.0`, lock its artifacts, and install that group in the isolated probe job. Do not change production dependencies or the selected cryptography version, substitute plaintext, or lower KDF parameters. This necessary primitive corrects the original assumption that existing dependencies sufficed. Require a synthetic local encrypted serialization/decryption check (wrong/missing password rejected) before another Windows mechanism run; preserve the first fixture failure.

## Unnamed job API correction
Pinned pywin32's CreateJobObject wrapper rejects a None name even though Win32 supports NULL for an unnamed job. Preserve the original unnamed, non-inheritable job using a narrow typed CreateJobObjectW(NULL,NULL) call and wrap its returned handle in pywin32's owned HANDLE. Do not introduce a named job, use undocumented empty-name equivalence, remove job containment, or alter timeouts. Safe failure diagnostics may add only fixed probe-module/function names and numeric line locations, never source text, frame values or raw exception strings.

## Installed loader contract correction
Stage A targets the measured system OpenSSH 9.5 key loader's exact `Enter passphrase: ` prompt. Do not accept arbitrary prompts or reuse this keygen literal for the later ssh.exe authentication phase. Pinned pywin32 exposes CancelIo rather than CancelIoEx; the probe issues and cancels each overlapped operation on the same thread with one pending operation per handle, so use the former and keep the existing bounded completion wait. This changes neither the authorization checks nor the timeout/acceptance criteria.
