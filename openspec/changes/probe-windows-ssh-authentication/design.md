## Scope and prerequisites
Run only after the independently reviewed Stage A mechanism. Use `%SystemRoot%/System32/OpenSSH/{ssh,sshd}.exe` as installed; no downloads, service start/install, account creation, privilege grants, global registry or authorized_keys edits. The test uses the current account with a temporary private AuthorizedKeysFile. Only a missing binary or an explicitly identified account/privilege prerequisite is BLOCKED. Unknown configuration/API/start failures are INCOMPLETE; once the fixture is listening, authentication/nonce/pin failures are measured FAIL. Preserve safe stage and numeric/exit metadata rather than guessing a permission cause. Do not claim that the user's Acetamido machine was tested.

## Temporary server
Use one owned protected-DACL directory. Generate a synthetic Ed25519 host key and client key. The server necessarily reads its synthetic host private key from this private fixture; no user key or production secret is used. Client key remains randomly encrypted per invocation through the proven Stage A carrier. Write private sshd config: loopback only, an OS-selected high port, exact HostKey, AuthorizedKeysFile and PidFile paths inside the owned fixture, an exact AllowUsers entry for the current simple runner account, StrictModes yes, public-key authentication only, PasswordAuthentication/KbdInteractiveAuthentication no, no forwarding/X11/tunnel and no user rc. No Include/default configuration or global administrators_authorized_keys override. ForceCommand is a fixed `cmd.exe /d /c echo` plus a generated alphanumeric nonce: successful output is the command-execution evidence, not arbitrary requested shell work.

Run `sshd -t -f <private-config>` first with a short bound, then `sshd -D -e -f <private-config>` in an owned kill-on-close job, using the same suspended-create/assign/resume primitive. Probe listener readiness within five seconds and check original server process remains live. Never alter service/rights on failure. Output remains private and bounded; public diagnostics contain fixed stage/error category/exit code only, not raw stderr, paths or key text. Close and reap this exact server job and remove only owned fixture files.

## Actual client and prompt
Reuse the installed fixed helper, protected one-use named pipe, exact live process-chain validation and per-call job. New Stage B entry point may reuse existing primitives, not a new agent/controller. `ssh.exe` runs with a fixed command, exact identity file and known_hosts containing only the generated server public key for `[127.0.0.1]:port`. Pass `-F none`, `StrictHostKeyChecking=yes`, `UserKnownHostsFile=<owned>`, `GlobalKnownHostsFile=none`, `IdentitiesOnly=yes`, `IdentityAgent=none`, `AddKeysToAgent=no`, `BatchMode=no`, `PreferredAuthentications=publickey`, `PasswordAuthentication=no`, `KbdInteractiveAuthentication=no`, `NumberOfPasswordPrompts=1`, no proxy/forwarding/control/local command, and a five-second connection timeout. Force the exact installed ASKPASS helper; no console or stdin fallback.

The 9.5 ssh.exe prompt is `Enter passphrase for key '<first 100 filename bytes>': `, unlike Stage A keygen's literal. Derive its expected value from the exact `-i` argument (fixture path is ASCII), never accept a general prefix or arbitrary prompt. Reject confirmation/notification modes. Source: [v9.5.0.0 sshconnect2.c lines 1469–1505](https://github.com/PowerShell/openssh-portable/blob/v9.5.0.0/sshconnect2.c#L1469-L1505). Do not log that prompt/path.

## Cases and fixed acceptance
1. Correct pin: real ssh.exe authenticates with the encrypted synthetic key; the original one-use broker releases once to the validated helper; exit zero and bounded stdout equals the fixed nonce. This is actual public-key authentication and command execution.
2. Wrong pin: otherwise equivalent fresh client uses a different generated host public key. It must exit nonzero, produce no nonce, and have zero helper release. Do not wait unconditionally for ASKPASS when the SSH process has already failed host validation.
3. Extra request: use the existing repeat fixture behavior during a real successful SSH authentication. The same authenticated helper asks AGAIN after acknowledging receipt; broker returns only refusal, total secret releases remains one, then actual SSH authentication/nonce still succeeds. This exercises extra IPC refusal under ssh.exe, not a claim that a server controls local key prompts. Exact invalid/confirmation helper prompt rejection remains covered by Stage A boundary checks.

Each client has a ten-second bound; total experiment at most sixty seconds. Stop at first failure; preserve incomplete versus measured rejection. Never retry to green, alter pinning, disable StrictModes or change the account/rights. Safe JSON records stage B, versions, executable-present booleans, fixtureComplete/candidateAccepted, exits, nonceMatched, releases and cleanup. No raw stdout/stderr or key data is published. Stage B does not prove Windows-to-Linux helper execution or GPU behavior. Those remain required product acceptance after the carrier is integrated.
