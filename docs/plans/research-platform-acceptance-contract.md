# 最终验收契约与每 PR 精简审查

2026-10-25，**用户已接受总体验收框架并授权实施，验收尚未执行**。真实参数按下文在正式运行前冻结。范围为[完整研究旅程](research-platform-delivery-plan.md)，不以分阶段交付缩减最终产品；实施遵循OpenSpec先规范后代码；本轮尚不调用付费模型或真实 GPU。以下步骤是测试设计，不是依赖未实现接口的空测试或通过 stub。

## 运行前冻结与结果规则

正式验收前记录一份版本化 run manifest：本契约版本、源码 base/head、应用与 core 版本、测试选择、fixture/数据版本、模型/provider/参数、身份系统、执行后端和目标机配置、预算、计时起止、故障注入点、用例与随机种子、样本数/配对顺序、观察窗口、通过线、清理范围和证据位置。测试操作者冻结后才启动；结果出现后不能调整通过线。改变用例或阈值须说明原因、另建版本，保留原失败，不把新线倒套旧结果。

尚待冻结：真实研究 use case 和评价指标、真实模型、实际身份服务、GPU/部署主机、样本数与重复次数、调用/token/金额/训练时间预算、科学指标容差、QA/投递/停止时间界限、通知上限、20 人负载组合与延迟/吞吐/资源门槛。没有实测依据时先做单独标为探索的测量，随后固定正式验收参数；探索不能计作正式 pass。不得凭空给成功率或容量阈值。单元契约中的零重复 dispatch、零越权等不变量不需要统计阈值。

| 结果 | 含义 |
| --- | --- |
| PASS | 精确版本在指定层级完成全部规定操作，断言和证据齐备 |
| FAIL | 任一硬不变量违反，或冻结的行为/质量/容量判据不满足；任务无进展超出冻结界限也算失败，不无限等待 |
| BLOCKED | 缺少真实依赖、访问授权或运行前冻结参数；保留阻塞原因，不解除对应最终门槛。若正在检验依赖故障恢复而产品未正确处理，则为 FAIL，不能归咎环境后豁免 |
| NOTRUN | 尚未执行，包括当前设计阶段；跳过不是通过 |

硬不变量必须在全部规定场景中 **100% 满足**，不能用平均分抵消越权、秘密泄露、重复副作用或预算绕过。`KNOWN-FLAKY` 只能是问题标签，不是结果，也不代表整套未失败。首次失败及每次重试均留原日志、配置、输入、时序与原操作身份；有界定位、修复后在新 head 复验受影响路径和必要集成检查，旧失败与修复证据关联。不得反复跑到一次绿后覆盖失败。

证据最小集：manifest、命令/操作与退出码、逐项结果（含跳过/阻塞）、请求/消息/任务/运行/产物关联、首失败时间线、必要截图/trace、清理结果。记录可见决策和工具轨迹，不要求模型隐藏思维链。秘密不得进入证据；无泄漏测试用可识别的合成 canary，真实日志只保留非秘密标识。下表每项均默认保留这些证据，再列专属证据。

## C：真实模型自主研究与团队价值

选用可由独立程序/人核对结果的真实小研究任务，模型读取实际实验输出后决定下一步；预写固定路线、fake 回答或将 oracle 答案放进 prompt 不满足本层。预算内未获得科学提升不自动失败；是否依据证据调整、正确停止、交付可信成果才是关键行为。隐藏 oracle、预期标签及标准答案只对被测研究 agent 不可见；独立只读验收评审者使用 oracle 与 rubric 核对来源和轨迹。被测 agent 仅接收正常用户目标与有权读取的证据，不接收测试裁判提示。评审者不能修改输入或指导运行中的 agent。

## 完成判定与 P0–P9 使用方式

各 PR 只运行其影响的上述 ID 及已有必要回归，不复制整套矩阵。不把每项叉乘全部成员、模型和故障；容量使用独立代表性工作负载。PR104 证据仅覆盖未改底座，不能替代新协作旅程。P0–P8 的局部 pass 不解除 P9 的 C/D 层最终门槛；最终集成版本要覆盖 A–D 全部适用场景，真实依赖未接入不得以 mock、skip、KNOWN-FLAKY 或旧 head 证据宣布产品通过。复用既有证据须写明源码/依赖/配置等价范围，不把旧完整通过外推到新代码。

每个执行记录列 ID、精确 head、结果、证据链接、首失败与修复关联。契约未覆盖的新行为先补明确判据再实施，避免事后为实现量身定验收。

## 每 PR 合入前独立精简审查：硬门槛

这是一项代码审查责任，不新增产品审批流或自动化平台。适用于 P0–P9 每个 PR；审查者必须不是该 PR 的作者，可由独立 agent 承担。检查 **相对指定 base 的完整 diff**（含新增、删除、测试、配置、依赖和文档），绑定精确 base/head SHA。不能仅看作者摘要、最后一个 commit、抽样文件或某模型品牌。

审查必须回答：

1. 每个新抽象、接口/扩展点是否有当前消费者与真实职责？能否用现有机制或直接实现？指出过早通用化、多层包装和为假想未来准备的成本。
2. 兜底分支是否有可信触发条件和可验证行为？检查低概率无依据特例、吞错、静默降级、重复 retry、双执行/恢复状态机；不是所有容错都应保留。
3. 校验、hash、缓存、注释和文档是否表达真实边界？去掉内部可信契约上的重复防御、无用途摘要、复述代码的注释与重复解释；不能机械按行数/复杂度或文件大小裁判。
4. 更简单的实现是否仍保留必要的权限、预算、凭据托管、原操作身份、UNKNOWN/停止证据保护？不能为了简化删除这些职责，也不把它们当作所有复杂性的通行证。
5. 测试是否检验独有失败风险，而非镜像实现/重复覆盖或空通过？本 PR 的验收 ID、首次失败和未运行边界是否如实？

每个发现需给 **file:line、具体复杂性成本、为何当前不需要、较简单改法、应保留的边界和验证方式**。结论必须是 `可合入（无未解决阻断项）` 或 `需整改（列明阻断项）`，并给判断理由；空模板勾选不算审查。建议优化与阻断问题分开；作者回应和实际整改可追溯。存在重大产品/架构取舍时交用户决定，不能用审查者偏好悄悄改需求。

修改后审查者复审受影响代码及交界，明确哪些旧结论仍有效。head 或 base 变化时重新判断旧审查是否失效；没有针对最终 head 的结论不得合入。重排/冲突解决也需检查，不能用旧 head 的 approved 或 CI 代替。最终检查结论、相关自动化和验收证据都绑定同一 head；未知、失败或未整改阻断项不能绕过。

最小审查记录：`base/head → 审查者（非作者） → 覆盖范围 → 具体发现/无发现的理由 → 必要整改及验证 → 最终 head 复审结论`。不规定发现数量；没有问题可以通过，但必须有实际完整 diff 判断。
