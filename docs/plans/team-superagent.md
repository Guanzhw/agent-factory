# 团队 SuperAgent 实施计划

团队成员各自保有研究助手、模型和工作空间。一次团队研究发现可以引出一项新工作，也可以改变另一位成员正在做的实验。用户从现有研究会话查看原因、贡献者、证据和结果。执行沿用 Agno 3.1.0 原生 Agent、队列和会话。Pi 的运行中补充与后续事项区分、Codex 的 thread/turn/action 记录用于指导交互。

## 工作归属

首个场景由甲的已有项目承担目标和交付。乙的助手以乙的身份回答，引用可共享的原始材料。多人共同接下一个目标时，团队可见的工作记录由发起成员负责收尾；其他成员的助手各自执行并回传成果。记录关联原项目、负责人、贡献者、源记录和各自的交付引用。个人执行过程仍归原成员。共享工作记录在第四步引入，前三步沿用已有项目、会话、问题和材料 ID。

## 交付顺序

1. **从队友的证据追问到结论。** 以 [#207](https://github.com/Guanzhw/agent-factory/pull/207) 的团队发布事件为入口。把来源和发布人带进甲的会话，沿用助手目录、同事问答和原会话自动续办。乙发出的实验结论缺少一个会改变判断的条件；甲的助手向实际发布者的助手追问，乙从另一条已共享的记录答复，甲在原项目里写出带出处的判断。条件已充分时可直接引用。验收要能从最终结论追到原始记录和实际答复；仅保存问题或启动任务算作中间状态。
2. **让助手发现并归置新工作。** 在成员开启主动发现后，让其助手结合项目目标、已有工作和新发布的团队材料，判断是否值得跟进。一次发布对一位成员形成一次可回查的决定：略过、附到现有工作，或围绕独立问题新建工作。记录所依据的材料、理由及目标会话。沿用原身份和既有会话创建、续办入口。用无关键词重合但实质相关的记录、表面相似却无关的记录及一个独立问题验收，核对各自去向与重复投递后的结果。
3. **让新信息在合适的时机被采用。** 同一问题的新证据在当前轮下一次模型请求时纳入；独立工作排在后面。若本轮已经结束且未采用该信息，则沿原会话续办一次。页面区分用户纠正、同事提供的证据和新任务，显示到达与实际采用的时刻。验收用一次正在调用工具的任务：中途抵达的事实改变下一次决策，另一件独立事项仍可单独跟踪。沿用真实 Stop 和已有的投递标识。
4. **让多个成员的助手交付同一项团队工作。** 在一条共享工作记录上提出目标，登记负责人并按需征集贡献。成员可看到谁正在处理什么、哪些结果已返回、哪些问题仍待回答。负责人综合贡献后发布带出处的交付。用两位成员分别贡献证据和复核意见验收，关闭、重开浏览器后仍能从团队记录找回两人的贡献及结论。

每步单独提交可运行的 PR。首先贯通第一个双成员场景，后一步按前一步的实际缺口实现。使用已有 PostgreSQL、浏览器和模型入口复现行为，优先扩展能看见用户结果的现有检查。脚本模型验证工具与投递链路；用团队成员实际配置的模型评估它是否会提出有价值的问题和形成有依据的结论，分别记录结果。新增安全机制与使用限制留到用户功能验收后再议。

设计依据见[团队研究需求](../../CONTEXT.md)、[自主 Agent 决定](agent-autonomy-20261106.md)和[同事问答验收](../../openspec/changes/research-autonomous-collaboration/verification.md)。
